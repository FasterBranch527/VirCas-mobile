# VirCas — состояние работ и дальнейший план

Дата: 7 сентября 2026. Рабочая ветка: `astra/vircas-new`.
База: `main` на коммите `7dd6c53ccd78bf00b1fa130f511d93e3a4a568dd`.

> Это промежуточная фиксация работы, а не готовый релиз. Часть экранов ещё не подключена к новой модели раунда. Новые Kotlin/Android-тесты и сборка пока не запускались. В `main` ничего не слито.

## Что было согласовано

Стабилизировать жизненный цикл раунда и сохранение виртуальных монет: поворот экрана, повторные callbacks, выход из игры, прерванная запись и перезапуск приложения. Это офлайн-аркада; задача не превращает её в банковский сервис или полноценную античит-систему.

Не менять шансы, коэффициенты, цены предметов/кейсов, правила игровых движков, оформление и физику монеты. Экономику Wheel, ключи подписи и остальные выводы аудита обсуждать отдельно.

## Что уже внесено в ветку

### 1. Журнал раундов и кошелёк в Room

Файлы: `core/game/WagerRules.kt`, `core/game/GameLedger.kt`, `core/data/LedgerData.kt`, `core/data/AppDatabase.kt`, `core/wallet/WalletRepository.kt`.

- Добавлены таблицы `wallet_state` и `game_wagers`; баланс больше не рассчитывается отдельной операцией от записи результата.
- Старая сумма из DataStore `wallet/balance` импортируется один раз. Уже существующая строка кошелька не перезаписывается при повторной инициализации.
- Начальная сумма остаётся **100 000 VC**.
- Резервирование ставки и создание раунда выполняются одной транзакцией.
- Повторное завершение возвращает исходную квитанцию и не начисляет выплату повторно. Отмена закрытого раунда не возвращает ставку ещё раз.
- Ревизия ставки защищает увеличение ставки от повторного применения устаревшего запроса.
- На одну игру допускается один активный зарезервированный раунд.
- Выплата, закрытие раунда, история, fairness-запись и необязательный предмет из кейса записываются одной Room-транзакцией.
- Продажа предмета объединяет удаление предмета и зачисление его прежней стоимости в одну транзакцию.
- Сохраняются исходные seed/client seed раунда, а не значения настроек на момент позднего callback.

### 2. Миграция базы

`VirCasApplication.kt` подключает `LEDGER_MIGRATION_3_4`, а `AppDatabase` имеет версию 4. Миграция добавляет новые таблицы, не удаляя существующие историю, инвентарь и fairness.

`fallbackToDestructiveMigration()` удалён. **Миграции более старых версий 1/2 пока не подготовлены**, полный тест обновления реальной базы версии 3 ещё нужен. Автоматический downgrade на старую версию приложения не предусмотрен.

### 3. Прогресс как повторяемое отражение завершённого раунда

Файлы: `core/game/RoundProgressSink.kt`, `core/progression/ProgressionRepository.kt`.

- Завершённый раунд получает признак ожидания синхронизации прогресса.
- ID раунда и изменения XP/счётчиков записываются одним DataStore-edit. Повторная обработка того же ID не повторяет начисления.
- Счётчики открытых кейсов и виртуальных ставок включены в эту же обработку.
- Ошибка обновления прогресса не отменяет уже проведённую выплату; обработка повторяется при следующем запуске/расчёте.
- Награды, цены, XP за обычный раунд и условия достижений не перебалансированы.

### 4. Состояние раундов и очередь сохранений

Файлы: `core/game/RoundMemory.kt`, `ui/RememberRound.kt`, `ui/AppViewModel.kt`.

- Добавлено хранение логического состояния в ViewModel: пересоздание Activity не обязано создавать новый раунд.
- Для длительных контроллеров есть coroutine scope, живущий вместе с ViewModel.
- Добавлены сохранение промежуточного/финального результата, последовательная очередь записей, повтор сохранения и защита от повторного нажатия Start во время резервирования.
- При новом ViewModel выполняется восстановительный расчёт журнала; запуск новых ставок блокируется до окончания восстановления.
- Для активного раунда можно получить его собственный поток RNG.
- При сбросе аккаунта очищается сохранённое в памяти состояние и меняется поколение, чтобы старые callbacks не использовались как новый раунд.
- Кейсы и виртуальные ставки переведены на новый расчёт; предмет кейса не добавляется отдельно от закрытия ставки.

## Как устроено восстановление — важное ограничение

Нужно различать два случая:

1. **Поворот/пересоздание Activity при живом ViewModel.** Подключённые экраны используют сохранённые логические объекты; анимация может начаться заново, но не должна создавать новый исход или вторую ставку.
2. **Полная смерть процесса/новый ViewModel.** Полная колода, доска и анимация не сериализуются для точного продолжения. Если в журнале есть checkpoint, он рассчитывается один раз; если checkpoint ещё нет, неиспользованная зарезервированная ставка возвращается один раз.

Терминальный checkpoint нельзя заменить старым cashout или возвратом. Нетерминальный checkpoint хранит текущий банк многошаговой игры. Для Crash ещё нужно подключить специальную политику: уже запущенный раунд без cashout сохраняет 0x, а не возвращает ставку при убийстве приложения.

**Вызов `checkpointWager` асинхронный.** Не считать сам факт вызова доказательством, что результат уже оказался на диске до первого кадра анимации. Требуется проверить порядок ожидания сохранения, показа результата и обработки ошибки в каждом экране.

## Как запускать проверки

Нужны JDK 17, Gradle 8.11.1 и Android SDK 35. В репозитории намеренно нет Gradle wrapper. Сборка также загружает закреплённые 3D-ассеты, поэтому нужен сетевой доступ.

```bash
git switch astra/vircas-new
gradle testDebugUnitTest --stacktrace
gradle assembleDebug assembleDebugAndroidTest --stacktrace
# После подключения эмулятора или тестового устройства:
gradle connectedDebugAndroidTest --stacktrace
# Сборка release — не означает готовность к публикации:
gradle assembleRelease --stacktrace
```

Текущий Android CI запускается на push в `main` и PR в `main`; обычный push в `astra/vircas-new` сам по себе его не запускает. Для проверки через GitHub можно открыть **draft PR**, без merge. Новая сборка/новый CI-прогон в рамках этой фиксации не подтверждены.

## Минимальная ручная матрица приёмки

| Сценарий | Ожидаемый результат |
| --- | --- |
| Двойной Start | Одна ставка и один активный раунд |
| Повторный callback settlement | Одна выплата, одна история, одна fairness-запись |
| Back после известного проигрыша | Нет возврата проигранной ставки |
| Поворот во время анимации | Тот же исход, без нового списания |
| Выход/возврат к Blackjack | Та же рука, без повторной раздачи и возврата ставки |
| Hi-Lo: Back после вычисления карты | Рассчитан pending-исход, не прежний банк |
| Coinflip: выход из серии | Рассчитан сохранённый банк/текущий исход |
| Crash: поворот/фон/Back | Время не начинается заново, cashout не берётся из устаревшего кадра |
| Убийство процесса после checkpoint | Сохранённый исход рассчитан один раз |
| Убийство процесса до checkpoint | Неиспользованная резервация возвращена один раз |
| Ошибка вставки истории | Не осталось отдельно начисленной выплаты |
| Ошибка прогресса после выплаты | Баланс правильный, прогресс повторяется без дубликата |
| Повторная продажа предмета | Предмет продан и зачислен только один раз |
| Сброс и поздний callback | Старый раунд не меняет новый аккаунт |
| Обновление базы 3 → 4 | Предыдущие данные сохранены |
